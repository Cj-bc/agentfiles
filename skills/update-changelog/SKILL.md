# update-changelog — コミットから履歴文書を追記する

**材料は git のコミットだけ**。あなたの記憶、会話の流れ、作業ツリーの未コミット変更は材料にしない。
仕事は「対象ファイルにまだ書かれていないコミットを見つけ、読んで、そのファイルの書式に合わせて
追記する」こと。**1 回の呼び出しで書き換えるファイルは引数で指定された 1 つだけ**。

**絶対規則**

- **既存の記述を書き換えない・並べ替えない・消さない。追記のみ。**
  リリース済みの節(バージョン見出しの配下)には一切触らない。
- **コミットに書かれていないこと・差分から読み取れないことを書かない。**
  断定できない影響は「要確認」と明記する。埋めるために推測しない。
- **自分では commit / stage しない。** Stop フックなどが要求しても実行しない。
  書き込みが終わったら差分を見せて、コミットはユーザーに委ねる。
- **対象ファイル以外を書き換えない。** 関連ドキュメントは検出して報告するだけ(フェーズ 5)。
- **文字コードと改行コードを保存する。** 対象が CRLF なら追記行も CRLF にする。
- 巨大な機械生成テキスト(シリアライズ済みシーン、ロックファイル、生成コードなど)は
  丸読みせず grep する。対象パターンはプロファイルが持つ。
- **このファイルに特定リポジトリの書式・規約を書き足さない。**
  それは `<repo>/.claude/changelog-profile.md`(プロファイル)の役目。

## 参照ファイル

| ファイル | 内容 | 読むタイミング |
|---|---|---|
| `<repo>/.claude/changelog-profile.md` | 対象ファイル・書式・節の対応表・関連ドキュメント表(リポジトリ固有) | フェーズ 0 |
| `references/profile-template.md` | プロファイルが無いリポジトリで新規作成するときの雛形 | フェーズ 7 |

## フェーズ 0 — 対象ファイルとプロファイルの確定

```
git rev-parse --show-toplevel        # 非 git なら理由を述べて停止
```

**cwd = リポジトリルートとは限らない**(サブディレクトリで起動されることがある)。
以降のパスはすべて `--show-toplevel` の結果を基準に組み立てる。

### 0-1. 対象ファイル

1. 引数にパスがあればそれを使う。**リポジトリルート基準 → cwd 基準**の順に解決を試し、
   どちらでも見つからなければ、近い綴りの候補を挙げてユーザーに確認して停止する。
   （勝手に新規作成しない。空ファイルへの追記は書式を推定できないため事故になる。）
2. 引数が無ければプロファイルの既定対象を使う。
3. プロファイルも無ければ、リポジトリルートの `CHANGELOG.md` / `CHANGES.md` /
   `HISTORY.md` を順に探す。無ければユーザーに尋ねて停止する。

対象ファイルの**現物を読んで**、書式・文字コード・改行コードを確認する。

```
file <target>                                   # UTF-8 / BOM / CRLF or LF
```

### 0-2. プロファイル

`<repo>/.claude/changelog-profile.md` があればそれが**正**。
無い場合は**対象ファイルの最新 2 節を読んで書式を採取する**(見出しの階層、箇条記号、
接頭辞の慣習、追記位置が節の先頭か末尾か、言語)。プロファイルを推測で新設しない
（作るのはフェーズ 7 でユーザーが同意したときだけ）。

## フェーズ 1 — 未記載コミットの範囲を決める

### 1-1. 基準コミット

```
BASE = git log -1 --format=%H -- <target>       # 対象ファイルが最後に書かれた地点
git rev-list --count $BASE..HEAD
```

「その履歴文書が最後に更新された後のコミット = まだ書かれていない変更」という前提で範囲を取る。
タグやバージョン番号に依存しないので、リリース運用が無いリポジトリでも効く。

引数で明示的にリビジョン/範囲が渡された場合はそれを優先する。
`BASE` が取れない(対象ファイルが未コミット)場合は、ユーザーに基準を尋ねる。

**この前提は破れることがある**:
- 対象ファイルが範囲外の目的でついでに触られていた → 範囲が短すぎる
- 前回の更新が一部のコミットを書き漏らしていた → 範囲が短すぎる

そのため**フェーズ 3 で必ず重複ガードをかけ、範囲はフェーズ 4 でユーザーに提示して確認する**。

### 1-2. 対象から外すもの

- **マージコミットの中身**: 内容の採取は `--no-merges` で行う(二重計上を防ぐ)。
  マージコミット自体はテーマの区切りとして 1-3 で使う。
- **対象ファイル自身だけを変更したコミット**: 履歴文書のメンテナンス。書くことは無い。
- **範囲内で打ち消されたコミット**(revert 対と、後続コミットで消えた変更):
  差分の**純効果**だけを書く。途中の往復は書かない。
- **作業ツリーの未コミット変更**: **範囲外**。ただし `git status --porcelain` で存在を確認し、
  「未コミットの変更 N 件は対象外」とフェーズ 4 の提示に必ず含める
  (書いたつもりの変更が漏れるのを防ぐため)。

### 1-3. テーマへの束ね方

**エントリはコミット 1 件 1 行ではない。テーマ 1 件 1 エントリ**に束ねる
(実装 + 追随修正 + テスト追加は、ふつう 1 つのエントリになる)。

束ねる手掛かり:

```
git log --first-parent --format='%h %s' $BASE..HEAD     # 幹の形。マージ = ブランチ名 = テーマ
git log --format='%h %s' <merge>^1..<merge>^2           # そのブランチのコミット
```

トピックブランチ運用ならマージコミットのブランチ名が最良のテーマ境界。
幹への直接コミットは、件名の接頭辞・対象ファイル・日付の近さで束ねる。

## フェーズ 2 — コミットを読む(材料採取)

**件名だけで書かない。** 件名は「何をしたか」しか言わず、「なぜ」「利用者に何が変わるか」を
持たないことが多い。本文が空のリポジトリではなおさら差分を読む必要がある。

テーマごとに:

```
git show --no-patch --format='%h %an %ad%n%s%n%n%b' <sha>   # 件名 + 本文
git show --stat --format='' <sha>                            # 触った範囲
git diff $BASE..HEAD -- <そのテーマのパス>                    # 純効果を読む
```

読み取るべきもの:

1. **何が変わったか** — 追加/削除/改名された型・メソッド・アセット・設定値
2. **なぜ** — 本文・issue 参照・課題管理 ID・コード中のコメント
3. **観測できる影響** — 利用者に見える挙動/見た目/音/タイミングの変化があるか、
   それとも開発者にしか見えない内部変更か(接頭辞の判断に使う)
4. **人間の確認が要るか** — 見た目・タイミング・音の変化、仮アセット、要差し替え
5. **参照 ID** — issue 番号、ロードマップ項目、ADR 番号

材料は scratchpad に `commits.md` として書き出しておく(同じ `git show` を何度も走らせない)。

パスを扱う git コマンドは **`git -c core.quotepath=false ...`** で呼ぶ。
既定では非 ASCII のパスが 8 進エスケープ + 引用符付きで返り、存在判定と比較が壊れる。

## フェーズ 3 — エントリの起草

### 3-1. 分類

プロファイルの対応表に従って各テーマを節へ振る(無ければ対象ファイルの既存節から推定する)。
**観測できる効果が無いテーマは書かない** — 整形のみ、WIP の往復、メモ、ローカル設定など。
迷ったら「この 1 行を読んだ人に判断材料になるか」で決める。

### 3-2. 書き方

- **言語は対象ファイルに合わせる**(日本語の文書に英語のエントリを混ぜない)。
- 1 エントリに「**何を変えたか → なぜ → 利用者/開発者に何が変わるか**」を入れる。
  既存エントリの粒度と文体を手本にする。既存が 1 行なら 1 行、既存が厚いなら厚く書く。
- シンボル名・パス・設定値はバッククォートで囲む。実在を確認したものだけ書く。
- issue / ロードマップ / ADR の ID は既存の書式どおりに付ける。
- **人間の確認が必要なものは、プロファイルの目印を付けて明示する**(見た目・音・タイミングの
  変化、仮アセットの差し替え待ちなど)。ここを省くと手動確認から漏れる。
- 断定できない影響は書かずに「要確認」と書く。**差分から読めないことを補完しない。**

### 3-3. 重複ガード(必須)

起草した各エントリについて、**対象ファイル全体**を検索して既出でないか確かめる。
フェーズ 1 の範囲推定が短すぎたり長すぎたりしても、ここで止まる。

```
grep -n -F '<シンボル名>' <target>      # クラス名・ファイル名
grep -n -E '#[0-9]+|RM-[0-9]+|ADR-[0-9]+' <target>   # 参照 ID(書式はプロファイル)
```

既出なら落とす。**部分的に既出**(前回エントリに続報が要る)場合は、既存行を書き換えるのではなく
新しい行として追記し、どの既存項目の続きかを本文で示す。

## フェーズ 4 — 確認(1 回だけ)

ユーザーに提示する:

- 対象ファイル / 基準コミット / 範囲のコミット数 / 束ねたテーマ数
- **起草した全エントリの全文**(節ごと)
- 書かなかったコミットとその理由(1 行ずつ)
- 重複ガードで落としたもの
- 未コミット変更の件数(対象外である旨)
- フェーズ 5 の関連ドキュメント検出結果

そのうえで AskUserQuestion で「この内容で追記する / 直す / 中止」を確認する。
**書き込む前に必ず一度止まる。** 履歴文書は人が読む前提の文書で、誤記は後から探しにくい。

## フェーズ 5 — 関連ドキュメントの追随検出(報告のみ)

範囲内のコミットに**構造の変更**が含まれるとき、それを説明している別のドキュメントは古くなる。
プロファイルの「関連ドキュメント表」を使って、追随が必要な箇所を**検出して報告する**。

検出の手掛かり(範囲の差分から):

```
git diff --name-status --diff-filter=ADR $BASE..HEAD    # 追加/削除/改名されたファイル
```

- 型・クラス・モジュールの追加/削除/改名、公開 API の増減、責務の移動
- ディレクトリ構成・ビルド設定・依存パッケージの変更
- 状態機械・フロー・ライフサイクルの変更
- テストの追加/削除(テスト一覧を持つ文書があるなら)

各対象について、**その文書が新シンボルに言及しているか grep で確かめる**。
言及が無ければ「追随していない」として、`文書 : 何が足りないか` の形で列挙する。

**この節では 1 文字も書き換えない。** 報告したうえで、
「続けてこれらも更新するか」をユーザーに尋ねる。同意があれば、**1 ファイルずつ**
フェーズ 0〜4 と同じ手順(対象を切り替えて)で処理する。

## フェーズ 6 — 追記

- 挿入位置はプロファイルの規則に従う(既定: 未リリース節の該当節の**先頭**)。
- 該当節が無ければ、プロファイルの節順に従って**新しい節を作る**。
  **同名の節を二重に作らない**。対象ファイルに既に同名の節が複数ある場合は、
  最上位のものに追記し、重複が存在することだけ報告する(既存の重複は直さない)。
- 未リリース節そのものが無ければ、最上位の見出しの**上**に作る。
- 改行コードを保存する。CRLF のファイルに LF 行を混ぜない
  (行単位の編集ツールが LF を入れてしまう環境では、書き込み後に
  `file <target>` と `git diff --stat` で行数が意図どおりかを確かめる)。
- 書き込み後に `git -c core.quotepath=false diff -- <target>` を表示し、
  **追記行数と、対象ファイル以外に差分が出ていないこと**を報告する。
- **commit しない。**

## フェーズ 7 — プロファイルの育成

- プロファイルが無かった場合、今回採取した書式・節の対応・関連ドキュメント表を
  `<repo>/.claude/changelog-profile.md` に残すことを**提案する**
  (雛形: `references/profile-template.md`)。書くのは同意を得たときだけ。
- ユーザーがフェーズ 4 で分類や文体を直した場合、その規則をプロファイルに追記することを
  提案する。同じ直しを毎回させないため。
