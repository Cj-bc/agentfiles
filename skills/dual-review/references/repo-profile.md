# プロファイル — エコシステム判定とリポジトリ固有ルールの採取

dual-review の骨格（SKILL.md）は言語非依存である。
**言語 / フレームワークに依存する知識は `profiles/<id>.md` に、
リポジトリ 1 つに固有の知識は `<repo>/.claude/dual-review-profile.md` にある。**
このファイルはその 2 つをどう見つけ、どう指示書へ流し込むかを定める。

```
SKILL.md（不変の骨格）
  └─ profiles/<id>.md          … 言語・ライブラリ依存（複数リポジトリで再利用できる）
       └─ <repo>/.claude/dual-review-profile.md … このリポジトリだけの事実
            └─ リポジトリの実物（CLAUDE.md / ADR / CI 設定 …） … 常に最新の正
```

下ほど優先度が高い。**衝突したら「下」を採る。**

---

## §1. プロファイルの解決

### 1-1. リポジトリ側プロファイル（最優先）

`<repo>/.claude/dual-review-profile.md` が存在すればそれを読む。書式は §3。
`profile_id:` が書かれていれば、対応する `profiles/<id>.md` も併せて読む
（リポジトリ側は言語プロファイルの**差分**を書く場所であって、置き換えではない）。

### 1-2. エコシステムの自動判定

無ければマーカーファイルで判定する。**上から順に評価し、最初に当たったものを採る**
（順序が重要: Unity プロジェクトは `.csproj` / `.sln` も生成するので、
`.NET` より先に Unity を見ないと誤判定する。実測で確認済み）。

| 順 | プロファイル id | マーカー | 同梱 |
|---|---|---|---|
| 1 | `unity-csharp` | `ProjectSettings/ProjectVersion.txt` | ✅ |
| 2 | `dotnet-csharp` | `*.sln` / `*.csproj`（Unity マーカーが無い場合） | — |
| 3 | `typescript-node` | `package.json` | ✅ |
| 4 | `python` | `pyproject.toml` / `setup.py` / `requirements.txt` | ✅ |
| 5 | `rust` | `Cargo.toml` | — |
| 6 | `go` | `go.mod` | — |
| — | `_template` | どれにも当たらない / 複数言語が混在 | ✅ |

「同梱」が `—` の id は `profiles/` にファイルが無い。その場合は `_template.md` の枠で進め、
`{{ECOSYSTEM_CHECKS}}` は §2 の採取結果と一般則だけで埋め、
**プロファイル未整備であることをユーザーに伝える**（勝手に新規プロファイルを書かない。
必要ならフェーズ 7 で提案する）。

複数当たる（モノレポ）場合は、**今回の diff が触っているパスに効くもの**を選ぶ。
たとえば `frontend/` だけの変更なら `typescript-node`。
2 つ以上のプロファイルが実質的に必要なら、両方読んで
`{{ECOSYSTEM_CHECKS}}` を連結し、そのことを指示書に明記する。

`profiles/<id>.md` が無い id を判定した場合は `_template.md` の枠で進め、
ユーザーにプロファイル未整備であることを伝える（勝手に作らない。フェーズ 7 で提案する）。

## §2. リポジトリ固有ルールの採取（毎回やる）

プロファイルがあっても無くても、**リポジトリの実物から次を集める**。
実在を確認したものだけ書く。**存在しないファイルを指示書に列挙しない**
（レビュワーが探して見つからず、時間を溶かすか、勝手に推測を始める）。

### 2-1. `{{CONVENTION_DOCS}}` — 先に読ませる規約ファイル

候補を `Test-Path` で確認し、**存在するものだけ**列挙する。

```
CLAUDE.md / AGENTS.md / CONTRIBUTING.md / README.md
.claude/knowledge/**  .cursor/rules/**  .github/copilot-instructions.md
docs/adr/**  doc/adr/**  **/adr/**  ARCHITECTURE.md  CHANGELOG.md
プロファイルの「規約ファイル候補」節にある追加パス
```

**規約ファイルの中に書かれたパスも検証する。** 規約ファイルは古びる。
たとえばあるリポジトリでは `AGENTS.md` が実在しないディレクトリを参照していた。
実在しないパスは指示書に載せず、代わりに
「`<doc>` には `<path>` とあるが実在しない。正は `<実パス>`」と 1 行添える。
この 1 行が偽陽性（「ドキュメントの参照先が壊れている」という無駄な指摘）を消す。

### 2-2. `{{TEST_LAYOUT}}` — テストの置き場所と実行方法

実際のディレクトリ構成から取る。規約ファイルの記述より**実物を優先**する。

- テストディレクトリ / 命名規則（プロファイルの既定を実物で上書き）
- テストの実行コマンド（`package.json` の scripts、`Makefile`、CI 設定から）
- **レビュワーにテストを実行させるかどうか**。既定は**実行させない**。
  実行が重い / 環境を壊す（エディタを閉じる必要がある、DB を要する等）場合は
  `{{EXTRA_PROHIBITIONS}}` に「実行するな」と明記する。

### 2-3. `{{ECOSYSTEM_CHECKS}}` — 言語 / ライブラリ依存のチェック項目

`profiles/<id>.md` の「レビュー観点」節をそのまま流し込む。
リポジトリ側プロファイルに追記があれば連結する。**ここに書いてないものを創作しない。**

### 2-4. `{{KNOWN_EXCEPTIONS}}` — 既知の例外（偽陽性の予防）

**最も効く項目。空で渡さない。** 次から集める。

1. `<repo>/.claude/dual-review-profile.md` の「既知の例外」節（あれば最優先）。
2. 規約ファイル / ADR に書かれた **意図的な逸脱**
   （「〜は例外」「〜は意図的」「deliberate」「by design」で grep すると速い）。
3. 既知の失敗テスト・既知の警告（CI 設定、README、ロードマップ、issue テンプレート）。
4. 規約ファイル同士の矛盾、古い記述（§2-1 で見つけたもの）。

各項目は **「何を指摘してはいけないか」+ 「なぜ」** の 2 点セットで書く。
理由が無いとレビュワーは無視する（あるいは理由を捏造する）。

### 2-5. `{{EXTRA_PROHIBITIONS}}` — 追加の禁止事項

rubric の共通禁止事項（書き込み・git 変更系）に足すもの。例:

- 重いビルド / テストランナーの起動禁止（エディタや排他ロックを壊すもの）
- 特定ディレクトリへの立ち入り禁止（巨大な生成物、資産、`node_modules` 相当）
- 外部ネットワークアクセスの禁止

## §3. `<repo>/.claude/dual-review-profile.md` の書式

リポジトリ固有の事実はここに置く。**スキル本体には書かない**（他リポジトリに漏れるため）。
リポジトリに checked in されるので、次回以降・他人の実行でも効く。

```markdown
---
profile_id: unity-csharp        # profiles/<id>.md のどれを土台にするか（省略可）
base_branch: develop            # 自動判定を上書きしたいときだけ（省略可）
---

# dual-review profile: <リポジトリ名>

## 規約ファイル
- `<path>` — <何が書いてあるか>
- **注意**: `<doc>` の `<path>` は実在しない。正は `<実パス>`

## テスト
- 置き場所: `<path>` / 命名: `<pattern>`
- 実行: `<command>`（レビュワーには実行させない / させてよい）

## 追加のレビュー観点
- <このリポジトリでだけ効く観点>

## 既知の例外（指摘してはならない）
- <事象> — <なぜ意図的か / どこで決まったか>

## 生成物・巨大ファイル
- <glob> — digest 対象 / 差分から除外

## 追加の禁止事項
- <レビュワーにさせてはいけないこと>
```

**書き込みのタイミング**: 監督がこのファイルを作る / 更新するのは
**汚染ガード（フェーズ 5）の後、かつユーザーの同意があるときだけ**。
レビュー中にリポジトリへ書き込むと自分の汚染ガードに引っかかる。

## §4. 移植時のチェックリスト

新しいリポジトリで初めて dual-review を回すとき、次を目視で確認する。

- [ ] base 判定が正しい候補を選んだか（`main` が無い / `develop` が幹のケース）
- [ ] エコシステム判定が正しいか（Unity と .NET の取り違えに注意）
- [ ] `{{CONVENTION_DOCS}}` に**実在しないパス**が混ざっていないか
- [ ] `{{KNOWN_EXCEPTIONS}}` が空になっていないか
- [ ] `{{TEST_LAYOUT}}` の実行コマンドが、レビュワーに実行させて安全なものか
- [ ] digest 対象の glob がこのリポジトリの生成物を捉えているか
      （捉え損なうとレビュワーのコンテキストが生成テキストで埋まる）
