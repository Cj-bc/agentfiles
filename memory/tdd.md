## 新 API を参照するテストは、先に書いても「落ちる」を見せられない
「まずテストを直して、落ちるのを確認してから実装」を静的型付け言語でやると、
**まだ存在しない関数を参照した瞬間にコンパイルが止まり、テストが 1 件も走らない**。
出るのは「26 件が期待値と違う」ではなく「そんな名前はない」だけで、
これは境界が動いた証拠にならない。

分け方:

1. **既存 API だけで書ける境界テスト** を先にコミットする → 実際に走って落ちる。
   失敗メッセージに「期待 = 新しい境界値 / 実際 = 古い境界値」が出るので、
   テストが正しい場所を突いている証拠になる。
2. **新しく増やす API とそのテスト** は実装と同じコミットに入れる。
   新関数のテストを先行コミットに置くと 1 の確認ごと潰れる。

コミットメッセージには「この時点で 167 件中 26 件が落ち、すべて境界ケース」のように
**落ちた件数と落ち方** を書き残す。後から履歴を見た人が、その赤が意図されたものだと分かる。

## ガードは mutation で確認する
「このガードは必要だ」と主張するテストは、**ガードを外して赤くなることを実際に確かめる**。
条件を `false` に潰して `test` を走らせ、狙ったケースだけが落ちるのを見てから元に戻す。
外しても緑のままなら、そのテストはガードを守れていない。

置換でコードを潰すときは括弧の対応に注意。壊れたコードはコンパイルエラーになるだけで、
「テストが落ちなかった」と見分けがつかない（出力が空になる）。
