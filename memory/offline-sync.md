## 各レプリカが「自動で」作るレコードには、生成元から決定的な ID を付ける（2026-10-30）
ユーザー操作ではなく、規則に従ってアプリが作るレコード（定期的な支出、月次の締め、初期データ、既定の設定など）は、
オフラインの各レプリカが同じものをそれぞれ作る。ID がランダム（UUID / ULID）だと、ID 単位のマージは別々の追加とみなして両方を残し、二重になる。
「何回作ったか」のような状態も両方で同じ値になるので、競合としても検出されない。

マージ側で「中身のこのフィールドが同じなら同一」と特別扱いするより、**生成元の自然キー（元レコードの ID + 期間など）から ID を作る**方が小さく済む:
- 同じ内容なら「両方が同じ追加」になり、汎用の 3-way merge が 1 件にまとめる。片方が後で変えていれば、普通の競合になる。マージは汎用のまま。
- 自然キーは、ユーザーが編集できるフィールド（日付など）から読み取らず、生成した時点の値で ID に焼き込む。編集後に別物と取り違えない。
- ULID のように ID に時刻を持つ形式では、時刻部分が作成時刻でなくなる。時刻で並べる箇所への影響を確かめる。

残る制限（設計時に書き出す）:
- 決定的 ID にする前の版が作ったレコードとは一致しない。
- 削除の記録（tombstone）がないと、片方が「作って消した」ものは祖先と同じに見え、相手の追加が残る。

## レプリカや版をまたいで同じ値になるハッシュは自前で書く
`kotlin.random.Random(seed)` は「同じ Kotlin ランタイムの版の中で」しか同じ列を保証しない（他言語の標準乱数も多くは同様）。
`nextInt(n)` のような変換も標準ライブラリ次第。保存して比べる値（ID など）に使うなら、FNV-1a などを数行で書き、ビットの取り出しも自分で行う。
期待値は別実装（Python など）で計算してテストに固定する。
80 ビットが要るときは、FNV-1a を 2 回（2 回目は 1 回目の結果を offset basis に）かけ、それぞれから 40 ビットずつ取った。
