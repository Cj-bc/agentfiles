## 端末が自動で作るレコードには、決定的な ID を付ける（2026-10-30）
tmp-budget-book の固定費は、起動時に端末ごとに「今月の支出」を自動で記録する。ID がランダムな ULID だったので、
2 台がオフラインで同じ月を適用すると、レコード単位の 3-way merge は ID の違う 2 件を独立した追加として両方残した（#40）。
マスター側の `lastAppliedMonth` は両方同じ値になるので、競合にもならない。

マージ側で「固定費 ID + 月が同じなら同一」と特別扱いする案より、**ID を元データ（固定費 ID と対象月）から作る**方が小さく済んだ:
- 同じ内容なら「両方が同じ追加」として既存のマージが 1 件にまとめ、片方が変えていれば既存の競合になる。マージは汎用のまま。
- ID に対象月を入れておけば、ユーザーが日付を翌月に動かしても別の発生と取り違えない（日付から月を読む同一視ではこうならない）。
- ULID の時刻部分は作成時刻でなくなる（対象月の初日にした）。時刻で並べる箇所への影響を確かめる。

残る制限（PR に書く）: 古い版が作ったランダム ID とは一致しない。片方が「追加して削除」したものは、祖先と同じに見えて相手の追加が残る（削除の記録＝tombstone がないため）。

## 端末・版をまたいで同じ値になるハッシュは自前で書く（2026-10-30）
`kotlin.random.Random(seed)` は「同じ Kotlin ランタイムの版の中で」しか同じ列を保証しない。`Random.nextInt(n)` の実装も stdlib 次第。
保存する ID に使うなら、FNV-1a などを数行で書き、ビットの取り出しも自分で行う。期待値は別実装（Python など）で計算してテストに固定する。
ULID の 80 ビットは、FNV-1a を 2 回（2 回目は 1 回目の結果を offset basis に）かけ、それぞれから 40 ビットずつ取った。
