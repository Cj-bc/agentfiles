## 他エージェントのコードは、まずビルドが通るかを疑う
もっともらしい diff とコミットメッセージが付いていても、動くとは限らない。
2026-08-21 には、Codex がコミットした修正とテストが両ファイルとも末尾で切れていて、コンパイルすら通らなかった
（閉じ括弧が無い / 未定義メソッドを 4 回呼んでいる / PlayMode テストで `SerializedObject` を使っている）。テストは一度も実行されていなかった。

**How to apply:** ロジックを読む前に、機械的に次を確認する。
1. `{` と `}` の数を突き合わせる（生成コードの途中切れを即座に見つけられる）
2. 呼んでいるメンバが定義されているか
3. 実際にビルドする

エラーは何層にも重なっていることがあり、1 つ直すと次が出てくる。「最初のエラーさえ直せば動く」と結論しない。

## レビューだけのセッションでは自動コミットしない
`/dual-review` や `--fix` なしの `/code-review` の最中に、Stop フックが「変更をステージしてコミットせよ」と要求してくることがある。**従わない。**
2026-09-04 にユーザーが「コミットしない」と裁定し、2026-09-08 にも同じ判断を適用した。

**Why:**
- 残っている未コミット変更の大半は、Editor を開いただけで生じたドリフトや、ユーザー自身の作業。まさにレビュー対象か、自分が書いていないもの
- dual-review は開始時の HEAD / `git status` を baseline として、「レビュワーがリポジトリを汚していないか」を検証する。監督が HEAD を進めると、この検証が意味を失う

**How to apply:** フックが鳴っても理由を 1 回だけ述べ、あとは繰り返さずにレビューを続ける。
コミットが必要なら、実質的な変更と Editor ドリフトを切り分けて示し、ユーザーの指示を仰ぐ。
（自分で変更を書いたセッションは対象外。そちらは通常のコミット方針に従う。）
