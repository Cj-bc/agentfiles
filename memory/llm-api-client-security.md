# LLM の API クライアントで API キーを漏らさない

flix-agent#6（Anthropic Messages アダプタ）は、セキュリティを重点にしたレビューを 3 回受け、毎回、再現テスト付きで別の漏れ方を指摘された。
「送り先を確かめる」「エラーに秘密を入れない」の 2 つを、最初から次の項目で確かめておくと手戻りが少ない。

## 送る前に確かめる（すべて HTTP を呼ぶ前に。どれかに当たれば何も送らずに失敗を返す）
1. **HTTPS か。** `http://` の `baseUrl` には送らない。
2. **このアダプタのモデルか。** ハンドラ（effect のハンドラ、ミドルウェア）がスコープ内のすべての呼び出しを引き受ける作りだと、
   モデルを切り替えたときや、ハンドラを重ねる順番を誤ったときに、別の API のモデル（ユーザーが自由に `baseUrl` を決められるもの）へキーを送ってしまう。
   モデルの API の種類を確かめる。
3. **キーを送ってよいホストか。** 種類が合っていても `baseUrl` は任意なので、設定にキーを送ってよい origin を持たせ（既定は公式の API）、一致するときだけ送る。
   比べるときは origin の直後の `/` まで含める。`https://api.example.com.evil.example`、`https://api.example.com@evil.example`、別ポートを弾ける。
4. **キーがヘッダーの値として正しいか。** ファイルから読んだキーは末尾に改行が残りやすい。HTTP ライブラリのヘッダー検証は、拒否したときに値をエラーメッセージに入れることがある（Java の `HttpRequest.Builder.header` がそう）。
   空や表示できる ASCII 以外の文字を含むキーは、自分で先に拒否し、キーを含まない固定の文で返す。

## リクエストの組み立て
- **リダイレクトを追わない。** 307 / 308 はヘッダーと本文（会話の全体）を保ったまま別のホストへ送り直す。3xx はエラーとして返す。
- **キー付きのリクエストを作る関数を公開しない。** 公開すると、上の確認を飛ばして使える。検証の後でしか呼べない場所に置く。

## エラーの文
- **返すエラーは、すべてキーを取り除く関数に通す。** 下の層（HTTP ライブラリ、サーバーのエラー本文）がキーを返してくることがある。エラーのすべての種類に当てる。
- **エラーに URL をそのまま入れない。** userinfo（`user:pass@`）に資格情報が入りうる。キーを取り除く関数は URL の中の資格情報までは隠さない。
- サーバーのエラー本文をそのまま返すと、長さに上限がなく、制御文字（ANSI エスケープ）も残る。端末に表示する側で無害化するか、ここで切り詰める。

## テストの書き方
- 偽の HTTP ハンドラで「HTTP まで進んだか」を記録し、拒否するべき入力で進まないことを確かめる。継続を呼ばずに打ち切れば、外には何も送られない。
- 漏えいのテストには、ダミーのキー（`sk-ant-DUMMY-SECRET` など）を使い、返したエラーの文字列にそれが含まれないことを確かめる。
- テストで本物の HTTP ハンドラを使わない。検証に漏れがあったときに、テストから実際の通信が起きてしまう。
